# Original File Preservation

Part of the root [maintenance contract](../MAINTENANCE.md).

## Intentional Divergence

Upstream deletion after file conversion uses the process-level `file_delete_after_retain` policy. This fork permits an individual bank to preserve source evidence through the existing hierarchical configuration resolver. Explicit `false` preserves original uploads. A bank-level `null` inherits the tenant/process policy; a tenant-level `null` inherits the process policy. Neither null becomes a resolved policy value, and other banks retain their existing default. The default remains `true` and deletion still occurs after conversion queues retention.

Upstream [#4367](https://github.com/vectorize-io/hindsight/pull/4367) preserves the downstream document's original-file association for store-owned banks. It does not provide bank-scoped preservation policy. No equivalent policy override was found in the 2026-10-01 upstream preflight at `ec39e10900c6a971f1a73cd37402228d5cccaa25`.

- **Coupled surfaces:** `config.py`, `config_resolver.py`, `_handle_file_convert_retain`, `BankTemplateConfig`, generated template contracts and the configuration documentation. Keep boolean validation, null inheritance and export/import roundtrips together.
- **Python convenience client:** Keep `file_delete_after_retain` in both `update_bank_config` and `aupdate_bank_config`, including sync forwarding and the request payload. Wrapper `None` means omitted, unlike an explicit null in the generated BankConfig API. The existing bank-config coverage checker and HTTP payload tests protect this mapping. Keep the original-file story on the convenience method so server-only support cannot conceal wrapper drift.
- **Failure boundary:** The file worker reconstructs the task's tenant/API-key/retry context and requests fresh, fail-closed configuration before conversion or queueing retention. A failed bank/tenant lookup, missing bank row or malformed persisted preservation override must preserve original bytes and fail the task. Validate the policy before ordinary stored-override coercion can discard it. An existing bank with empty/null config still inherits. Ordinary resolver callers retain their best-effort fallback behavior.
- **Regression:** The exact-SHA gate includes `test_file_preservation_policy.py`, `test_hierarchical_config.py` and `test_bank_template_full_roundtrip.py`. The public-client story `hindsight-system-tests/tests/test_11_original_file_policy.py` uploads a file, waits for the real worker and background consolidation, then uses supported export/download APIs to verify original bytes and default deletion.
- **Adopt Or Retire:** Adopt an upstream equivalent only when it passes bank isolation, boolean/null inheritance, fresh failure-safe policy resolution, document association and public-worker preservation regressions. Remove this support unit when the equivalent replaces every covered surface.
- **Deployment:** Source inclusion is not runtime adoption. Before recovery submissions, deploy through the runtime owner, set only the intended bank's preservation policy through the normal API and read it back. A process-global policy change is a separate action.

## Lossless Administrative Rename

`hindsight-admin rename-bank` keeps the existing native row identities and SQL/store ownership boundary. It copies known live attachment, document and retry file keys with conditional create, then retargets rows and failed/cancelled execution payloads in the same database transaction. Only native execution fields change: `bank_id`, `storage_key` and `_file_metadata.file_storage_key`. Completed payloads, result metadata, user content and historical capsule snapshots/hash commitments are not rewritten.

- **Writer Exclusion:** The command takes `ACCESS EXCLUSIVE` locks on the schema's bank-bearing tables and native file storage, blocking readers as well as writers and row-locking claims. Taking the DDL-strength locks before copying avoids lock-upgrade deadlocks with queued writers. Lock acquisition times out after 5 seconds. Locks remain held through copying and commit. This is schema-wide maintenance downtime, not an online migration. Stop API clients, workers, migrations and external object writers before invocation and keep admission frozen until their bank configuration and caches have switched. Locks cannot stop a stale client from creating a fresh old-id bank after commit. No alias or tombstone is added.
- **Rollback And Dry-Run:** Temporary FK deferrability changes, row/key rewrites and native PostgreSQL blob copies share the rename transaction. Dry-run only checks catalogs, references, destinations and counts. It never executes UPDATE/rollback, DDL or blob writes, since sequence/trigger effects can survive a rollback. Existing destination banks, aliases or known destination objects fail before any write. Conditional create also refuses an object that races preflight.
- **Original Bytes:** No old-prefix sweep is performed. Attachments/documents alone are not an exhaustive inventory: completed history, retry tasks, exports and unsupported objects can still name the old keys. Original bytes remain after success and failure. New live copies follow normal document/bank deletion ownership. Retained old keys are deliberately not reclaimed by deleting the renamed bank, and can consume additional storage. Do not delete them based on that incomplete inventory.
- **External Storage:** S3/GCS/Azure use the existing obstore abstraction's atomic create mode, never an overwriting put. These creates cannot join PostgreSQL rollback. A partial copy or lost response can leave destination orphans, but not deleted originals or partially committed row references. A repeat refuses collisions rather than guessing that an orphan is safe to replace. A lost COMMIT acknowledgement can leave a fully committed rename, so inspect the bank and operation rows before repeating it. The deterministic object-store fixtures prove abstraction-level behavior, not provider deployment behavior or a restored-live-state rehearsal.
- **Curation:** Applied curation capsules fail closed. Their before/after snapshots and receipts bind bank ids and hashes, and there is no rename-aware domain operation. Resolve them using the supported curation recovery/revert workflow or add and qualify native rename-aware curation support before activation. Do not text-replace serialized capsules or their hashes. Other banks' capsules and historical snapshots remain unchanged.
- **Index Recovery:** Vector indexes are reconciled after commit using the existing store-owned index boundary. An exception or reported failed build returns a failed command with an explicit committed-state message and `repair-bank --bank <new-id> --schema <schema>`. Do not repeat rename-bank to repair indexes. Keep admission frozen until the native repair succeeds.
- **Regression:** Run `test_admin_rename_bank.py`, `test_attachment_lifecycle.py` and `test_hnsw_indexes_store_owned.py` against the repository's guarded ephemeral PostgreSQL fixtures, in addition to the exact-SHA local gate. These cover executable retry/claim payloads and exact bytes, immutable evidence/identities, collision zero-effects, nonmutating dry-run, copy/repoint/catalog/commit failure, writer barriers and explicit index repair. No production API or database is part of qualification.

### Upstream Reconciliation

Upstream [#4392](https://github.com/vectorize-io/hindsight/pull/4392) separated FK flips to limit lock duration. That rationale is valid for availability, but it permits persistent catalog changes on crash and makes dry-run mutate the catalog. Rename now keeps those flips inside the maintenance transaction and accepts the documented writer exclusion instead. Upstream [#4573](https://github.com/vectorize-io/hindsight/pull/4573), addressing [#4502](https://github.com/vectorize-io/hindsight/issues/4502), copied row-backed files and swept the old prefix to avoid storage leaks. The live-key copy/repoint and new-bank deletion ownership remain. The destructive sweep is intentionally removed because it cannot prove that retry/history/unsupported references are absent. Adopt a future upstream equivalent only when it passes the losslessness, rollback and nonmutating dry-run regressions, not merely row-backed leak cleanup.
